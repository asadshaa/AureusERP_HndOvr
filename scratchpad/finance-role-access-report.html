Findings & Fixes

Everything below surfaced from actually operating the app as each role, not from a code read. The first four are real authorization bypasses — a role with view-only permission could still submit a real write through the UI. All four were fixed and re-verified live during this session.

F1 — Vendor creation broken for every user
Fixed
3 migrations that add tax-identity columns existed on disk but were never applied to the live database. Every Vendor creation, by any role, failed with a DB error.
Found during AP Officer test 1.2 · fixed by applying the missing migrations
F2 — Manual Adjustments: unguarded Create button
Fixed
The header "New manual adjustment" button had no authorization check — unlike the direct URL, a modal action bypasses Filament's built-in route protection entirely. A view-only role (Internal Auditor, VP Finance) could actually submit a new adjustment.
ListManualAdjustments.php
Found during Internal Auditor test 3.2
F3 — Journal Entries: same unguarded Create button
Fixed
Identical gap on the Journal Entries list — the Internal Auditor could open and submit the create-entry modal despite holding view-only access.
ListJournalEntries.php
Found alongside F2
F4 — Vendor → Bank Accounts: unguarded, and with no backstop at all
Fixed
The worst of the three — this action lives inside a relation manager with no dedicated route to fall back on, so nothing protected it. Any role that can view a vendor (including Internal Auditor) could add a real bank account to it.
BankAccountsRelationManager.php
Found alongside F2
F5 — Oversight roles could see almost nothing
Fixed
Test accounts for Controller, Internal Auditor, and VP Finance were scoped to "individual" record visibility — meaning each could only see records it had personally created. For a pure oversight role that's structurally always zero. Corrected to company-wide visibility on all three accounts.
Found during Internal Auditor test 3.x, when the Journal Entries list appeared empty despite 19 posted entries existing
F6 — Manual Adjustments has no read-only view page
Follow-up queued
A role with view-only access can see the list but can't open an individual record — there's no view route to send it to. Not a leak, but it defeats the purpose of granting read-only visibility in the first place.
Found during Internal Auditor test 3.3
F7 — Reconcile / Unlink actions have no permission check
Follow-up queued
On any Invoice, Bill, Credit Note, or Refund page, the "Add" (reconcile) and "Unlink" (un-reconcile) buttons are wide open to anyone who can view the page — including a purely read-only auditor. This is a real data-integrity risk spanning five resource types in the base accounts plugin, scoped for its own review rather than a rushed fix.
First noticed during AP Officer test 1.6, root-caused during Internal Auditor testing
F8 — Same unguarded-button pattern swept for the rest of the plugin
Follow-up queued
Report Templates, Business Rules, FS Tags, Party Classifications, and Import Profiles all use the same unguarded Create-button pattern as F2–F4. None are currently reachable by any of the four tested roles, so there's no active exposure today — queued so the fix lands before any role's permissions change.
Identified via a codebase-wide grep after F2–F4
