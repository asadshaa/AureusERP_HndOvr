Technical Research · Not for implementation

Peer-to-Peer Connectivity for Aureus ERP

An architecture investigation into whether Windows ↔ macOS peer-to-peer communication should be added to Aureus, which technologies are viable, and what it would cost to do safely alongside an authoritative Laravel/MySQL ledger.

Scope · 6 P2P definitions, 14 technologies, 5 architectures Stack · Laravel 13.8.0 · Filament 5.6.3 · Livewire 4.3.0 · PHP 8.3 Status · Awaiting review — no code written

Evidence labelling used throughout

  • Verified  Confirmed against current official documentation or vendor pricing.
  • Repo  Observed directly in this codebase, with file paths.
  • Inference  Engineering judgement derived from the two above.
  • Assumption  Unverified premise that would change the conclusion if wrong.
Section 1 · Executive summary — conditional no-go

Do not build peer-to-peer connectivity into Aureus now. Not because P2P cannot be made to work between Windows and macOS — it demonstrably can — but because in this codebase P2P would be the most complex available solution to problems that are currently unsolved by far cheaper means, and because the target deployment environment is the one where P2P degrades worst.

Three repository findings drive that conclusion. Aureus has no realtime transport of any kind — no broadcasting config, no channels file, no Reverb/Pusher/Echo, and zero broadcast events. It has no desktop application — the NativePHP dependency is a mobile WebView shell wired only to the barcode scanner. And its document pipeline caps files at 20 MB and buffers each one entirely in memory, with no chunked, resumable, or truly streaming path anywhere. The "large file" pain that motivates P2P is therefore already broken server-side, well below the size at which peer transfer would begin to pay for itself.

Against that, the decisive external number: in corporate environments with managed firewalls, 60–70% of WebRTC sessions fall back to a TURN relay Verified. A relayed session is not peer-to-peer — it is centralised communication with extra steps, paid for in relay bandwidth. Building WebRTC for Windows-and-Mac office users means building the full complexity of peer connectivity and then routing the majority of it through a server anyway.

The recommendation is therefore Option E (Hybrid), deferred behind three prerequisites: fix the file pipeline, add server realtime via Reverb, and close the API tenant-isolation gap this review uncovered. If the real requirement turns out to be "devices on different networks must reach each other," the correct answer is not application-level P2P at all — it is Tailscale or self-hosted Headscale, which solves it at the network layer with zero application change.

Section 2

Current Aureus architecture, as it bears on P2P

Every finding below was read out of the repository during this review. They are stated first because most of them foreclose options that would otherwise look attractive.

What exists

  • Request path is entirely classic server-rendered Laravel: browser → Nginx → PHP-FPM → Filament/Livewire → Eloquent → MySQL. Repo
  • Authentication is session-based across two Filament panels (admin on guard web, customer on guard customer), with multi-factor authentication enabled via AppAuthentication::make()->recoverable() in AdminPanelProvider.php. Repo
  • Sanctum is live and issues bearer tokens from POST admin/api/v1/login; a REST surface exists under admin/api/v1/* across nine plugins behind auth:sanctum. Repo
  • Authorization stacks three layers: spatie/laravel-permission name checks, ~40 policy classes, and a row-level resource_permission scope (GROUP/INDIVIDUAL/GLOBAL) applied through HasResourcePermissionQuery on 23 resources. Repo
  • Documents are genuinely well-built and already contain most primitives a P2P transfer would need: SHA-256 per version, immutable version rows (an updating hook throws), write-verify after put(), read-verify via readVerifiedBytes(), a MIME allowlist, a company-prefixed storage layout, and an append-only accounting_document_audits table capturing actor, action, metadata and IP. Repo
  • Storage is already abstracted behind DocumentStorageProvider with a driver-agnostic implementation over the accounting_documents disk, switchable local↔S3 by DOC_STORAGE_DISK. Repo
  • Queue runs on the database driver with one job class (SyncDocumentToDriveJob, 5 tries, backoff 30s→1h). Repo

What does not exist — the constraining findings

  • No realtime anything. config/broadcasting.php and routes/channels.php are both absent; BROADCAST_CONNECTION=log; no class implements ShouldBroadcast; Filament's broadcasting.echo block is commented out; laravel-echo and pusher-js are absent from package.json. Repo
  • No client-side application to build into. package.json declares no runtime dependencies — only Vite, Tailwind, axios and concurrently as devDependencies. resources/js/app.js is a single import line. The only substantive project JavaScript in the repo is a vendored barcode scanner. Repo
  • No desktop native shell. Only nativephp/mobile is required — there is no nativephp/electron or desktop package, no config/nativephp.php, no committed build directory, and no Native:: facade call anywhere. The bridge is a WebView JS shim exposing vibrate() and toast() for /admin/barcode. Repo
  • No large-file capability. MAX_FILE_SIZE_BYTES is 20 MB; uploads run file_get_contents() then put(), holding the whole blob in memory; Drive uploads use Google's single-request multipart rather than resumable; and the streamDownload() calls stream a string that is already fully in memory. No chunked, resumable or multipart handling exists. Repo
  • No device concept. No device table, token-per-device, or fingerprint. Sanctum tokens are all named api-token and config/sanctum.php sets expiration => null, making them permanent undifferentiated bearer credentials. Repo
  • Deployment is HTTP-only. docker-compose.yml publishes exactly one external port (8080→80); MySQL is bound to loopback; there is no Redis, no WebSocket service, and nothing listening on UDP. Repo
  • No P2P precedent. An exhaustive case-insensitive sweep for WebRTC, DataChannel, STUN/TURN, signalling, libp2p, mDNS, Bonjour, multicast, Tailscale, WireGuard and QUIC returned only false positives inside minified vendor bundles and unrelated words such as smallestUnit. Repo
Two pre-existing security findings that must be fixed before any peer feature. First, the REST controllers expose company_id as a client-supplied AllowedFilter::exact() rather than deriving it from the token holder — so the API layer currently has no enforced tenant boundary, only a permission check. Any P2P grant issued through that layer would inherit the hole. Second, Webkul\Security\Bouncer caches authorized user IDs in a static property, which is per-process rather than per-user and will leak across users inside a long-lived worker — exactly the execution model a signalling service would introduce. Repo

The single most common failure in this class of project is treating these as one feature. They have almost nothing in common beyond the word "peer," and they carry wildly different risk.

Section 4

WebRTC DataChannels — the detailed case

WebRTC is the only technology in this review that can create a direct peer connection from an unmodified browser, which makes it the default candidate for a zero-install ERP feature. A DataChannel carries arbitrary bytes over SCTP, inside DTLS, over an ICE-negotiated UDP (or TCP-fallback) path.

Cross-platform and cross-browser reality

  • Chrome, Edge, Firefox and Safari all implement RTCDataChannel; a Windows Chrome peer and a macOS Safari peer interoperate, because the negotiation is standardised at the protocol level rather than the browser level. Verified
  • Encryption is mandatory and cannot be disabled — DTLS is part of the WebRTC specification, not an option. This is a real and often-understated security advantage over hand-rolled sockets. Verified

How connection establishment actually works

ICE (Interactive Connectivity Establishment) gathers three kinds of candidate address and then probes pairs of them:

  • Host candidates — the machine's own local addresses. These make same-LAN connections work.
  • Server-reflexive candidates — discovered by asking a STUN server "what public address and port do you see me from?". STUN is stateless, cheap, and carries no user traffic.
  • Relay candidates — obtained from a TURN server, which forwards every packet on the peers' behalf when no direct path can be found.
The honesty requirement the brief demanded. A TURN-relayed DataChannel is not direct P2P. Packets traverse a server you operate and pay bandwidth for; the only thing preserved is end-to-end encryption, which means the relay cannot read the payload but absolutely does carry it. Published measurements put relay usage between 0% and 50% depending on population, ~22% in one general study, and 60–70% in corporate environments with managed firewalls — driven mainly by outbound UDP being blocked. Roughly 85% of WebRTC connection failures trace to NAT/firewall traversal. Verified

The standard mitigation is to run TURN over TCP on port 443 with TLS, which corporate firewalls rarely block because it is indistinguishable from HTTPS Verified. That rescues connectivity but is precisely the configuration in which "P2P" has become a TLS tunnel through your own datacentre. Inference

Can Laravel be the signalling server?

Yes, and it should be. Signalling is just authenticated message relay: peer A's SDP offer and ICE candidates must reach peer B and vice versa. Requirements are modest — a handful of messages over a few seconds — so the transport does not need to be fast, only authenticated.

  • Laravel/Livewire can do it over plain HTTP with short polling. Ugly but entirely workable, and it adds zero infrastructure. Inference
  • Reverb is the better transport if realtime is being added anyway. Laravel 13 ships Reverb as the first-party broadcasting driver alongside Pusher and Ably, all speaking the Pusher protocol with Laravel Echo on the client. Verified
  • Laravel's broadcasting has no P2P or WebRTC capability of its own; the only client-to-client feature, Pusher "client events" via whisper(), still routes through Pusher infrastructure. So Reverb would be carrying signalling, not payload. Verified

How peers get authenticated — the crux

WebRTC itself authenticates nothing about identity. What it guarantees is that the DTLS session terminates at the endpoint whose certificate fingerprint appeared in the SDP. That is the hook: because the SDP travels through Laravel over an authenticated HTTPS session, and Laravel knows which Aureus user each socket belongs to, the fingerprint becomes a binding between a verified application identity and a transport session. Compromising it requires compromising the signalling channel — the same trust boundary as the rest of the ERP. Inference

Large files over a DataChannel

  • Maximum message size is negotiated by the SDP max-message-size attribute (RFC 8841); if absent, 64 KB is assumed, and most modern browsers support at least 256 KB. Verified
  • Without message interleaving (RFC 8260), one large message causes head-of-line blocking that delays every other channel. Verified
  • Therefore files must be chunked — 16–64 KB is the safe interoperable range — with flow control driven by bufferedAmount and the bufferedAmountLow event, or the sender will exhaust memory on a fast link. Inference
  • Resume requires an application-level protocol: chunk indices, a per-transfer manifest, and a persisted byte offset. Nothing in WebRTC provides this. Inference

Verdict on the proposed architecture. Laravel for authentication and signalling, with a DataChannel carrying payload directly between a Windows browser and a macOS browser, is viable and correctly shaped. It is the right design if the feature is built. The objection is not to the architecture but to its cost/benefit in this codebase at this time. Inference

Section 5

libp2p — capable, and not justified here

libp2p is the modular networking stack extracted from IPFS: pluggable transports, stream multiplexing, Noise/TLS security, persistent cryptographic peer identity, DHT-based peer discovery, circuit relay, and DCUtR hole punching. It is genuinely the most capable option in this review.

  • WebRTC support is documented as "implemented, available and documented" in js-libp2p and go-libp2p; rust-libp2p is not listed for it. Browser→server uses WebRTC-Direct, encoding the server's TLS certificate fingerprint into the multiaddr to simplify signalling; browser↔browser works via relay-based SDP exchange. Verified
  • The documentation is explicit that browsers cannot access raw UDP or TCP sockets, which is why WebRTC is one of very few viable browser transports at all — a constraint, not a libp2p limitation. Verified
  • Best runtimes are Go or Rust for native peers and js-libp2p in the browser or Node. Verified

What adopting it would actually require

There is no meaningful libp2p implementation for PHP. Laravel could not be a peer; it could only be a bystander issuing credentials to a separate service. That service is a new long-running daemon in a new language, with its own build toolchain, deployment unit, health monitoring, upgrade path and security surface — added to a stack whose entire production footprint is currently PHP-FPM, Nginx, a queue worker, a scheduler and MySQL. Section 6

Tailscale / WireGuard — the pragmatic alternative nobody asked for

WireGuard is a minimal modern VPN protocol (Noise-based crypto, tiny attack surface, kernel-fast). On its own it needs manual key exchange, explicit peer endpoints, and does not traverse NAT gracefully. Tailscale is the control plane that fixes all three: identity-based enrolment with SSO, automatic key distribution and rotation, NAT traversal with DERP relays as fallback, ACL policy, and MagicDNS naming.

  • First-class Windows and macOS clients; direct WireGuard tunnels where possible, encrypted DERP relay where not. Traffic is end-to-end encrypted, so relays carry ciphertext only. Verified
  • Pricing (2026): Personal free; Personal Plus $5/mo up to 6 users; Starter $6/user/mo; Premium $18/user/mo annual ($20 monthly) adding SSO/SAML, advanced ACLs and audit logging; Enterprise on quote. Verified
  • Headscale is an open-source control-server implementation, which removes the vendor dependency and per-seat cost at the price of running it yourself. Inference
The key reframing. Tailscale does not add peer-to-peer semantics to Aureus. It makes the network flat, so ordinary client-server HTTP works between any two enrolled devices regardless of NAT. For most organisations that say "we want P2P," this is what they actually want — and it requires no application code at all. The existing Nginx/Laravel stack becomes reachable device-to-device unchanged. Inference

The blocking objection is that it requires installing networking software with elevated privileges on every participating machine. For managed corporate fleets that is an MDM push; for BYOD, contractors, or customers whose IT forbids third-party VPN clients, it is a hard stop. It also does nothing for offline operation. Inference

Section 7

LAN discovery — why the browser cannot do it

The desired experience — open Aureus on Windows and see "MacBook — Asad's device — available" — is the part of this brief that is least achievable in a browser, and the reason is a deliberate privacy decision rather than a missing feature.

  • Chrome introduced mDNS obfuscation of ICE host candidates in 2019: instead of exposing 192.168.1.42, the browser registers and advertises a random hostname such as a1b2c3d4.local. Other engines followed. Server-reflexive and relay candidates are unaffected, since those already carry public addresses. Verified
  • Consequently JavaScript cannot read local IP addresses, and there is no browser API for mDNS/DNS-SD service browsing at all. Browser-only LAN device enumeration is not merely hard — it is closed by design. Verified
The saving nuance. Obfuscation does not prevent LAN connectivity. The browser's own ICE agent resolves those .local names internally, so two peers on the same subnet still connect over host candidates at full LAN speed — the page simply never learns the addresses involved. LAN transfer via WebRTC works; LAN discovery via WebRTC does not. Inference

Real discovery therefore requires a native agent using Bonjour on macOS or the built-in mDNS responder on Windows 10+. Two further obstacles apply even then: corporate WLANs commonly disable multicast or enable wireless client isolation, which breaks mDNS regardless of implementation; and shipping a native agent means two signed, auto-updating desktop builds that do not exist in this repository today — the NativePHP dependency present is mobile-only. Repo Inference

Practical substitute. Because Aureus already knows every authenticated user and (with a device table) every registered device, presence can be derived server-side — "Asad's MacBook, last seen 30 seconds ago, same office network by public-IP match" — and rendered as a device picker. This delivers the intended UX with no discovery protocol at all. Inference

Section 9

Security architecture

The governing principle. A peer connection must never, under any circumstance, imply authorization. Establishing a DTLS session proves only that the other endpoint held the certificate fingerprint exchanged during signalling. It proves nothing about who that user is, which company they belong to, or what they may read. Every payload must be authorized by the server before the transfer, and verified cryptographically after it.

Device identity — net-new, but with a foundation

Aureus has no device concept today, so this must be built. The natural shape is a user_devices table holding a server-assigned id, the owning user and company, a device-generated public key, a human label, platform, last_seen_at, and revoked_at. Private keys are generated on the device and never transmitted — WebCrypto with a non-extractable key persisted in IndexedDB for browsers, Keychain or DPAPI for a native agent. The existing personal_access_tokens table is a reasonable companion, but only after fixing the two defects found in this review: tokens are all named api-token, and expiration is null, making them permanent. Repo Inference

Authorization via short-lived capability grants

The correct primitive is a server-signed, single-use, short-lived transfer grant — not a persistent peer trust relationship. It should carry: grant id and nonce, sender user and device, recipient user and device, company_id, the specific document_id and its expected SHA-256, a byte ceiling, the expected DTLS fingerprint, and an expiry measured in minutes.

This design puts every access decision back where it belongs. The server evaluates the existing AccountingPermissions checks and company isolation before issuing anything; the peers merely execute a transfer that has already been authorized. Binding the expected fingerprint into the grant lets each peer verify that the connection it is actually on is the one the server blessed, which is what defeats substitution and man-in-the-middle attempts at the signalling layer. Inference

An irreducible weakness, stated plainly. When bytes move peer-to-peer, the server does not observe the transfer. It can log that it authorized one and collect signed completion attestations from both peers (hash, byte count, duration), but it cannot independently prove what was actually transmitted. For an ERP whose document subsystem currently records every view and download in an append-only audit table, this is a genuine reduction in auditability — and for regulated financial records it may be disqualifying on its own. A reviewer should weigh this before any technical consideration. Inference

Section 10

Accounting safety, and why offline ledgers are a different class of problem

The brief's initial assumption was that P2P should never directly mutate authoritative accounting data. That assumption is correct, and it can be proved rather than asserted.

Four invariants that require a single serialization point

  1. Gapless sequential numbering. Journals and invoices carry per-company, per-journal sequences — this repository's own records show BILL/2026/27 and MISC/2026/25, and its auto-naming overrides a caller-supplied name. A gapless sequence is a global invariant: it cannot be allocated on a disconnected device without either coordination (which defeats disconnection) or post-hoc renumbering (which invalidates any reference already issued to a vendor or tax authority). Repo
  2. Balance and control totals. Two devices can each create individually valid entries that jointly breach a period control total. Validity is not composable.
  3. Period locks. Posting into a closed period is illegal, and a disconnected device cannot know the period closed ten minutes ago.
  4. Approval semantics. An approval binds a person, a role, a moment, and a specific version of a record. It is not commutative and has no merge function — approving offline a record that changed server-side is either meaningless or dangerous.

Why CRDTs do not rescue this

Conflict-free replicated data types work by guaranteeing that concurrent states can always be merged deterministically. That is exactly the wrong shape for a ledger. A posted journal is immutable by design in this codebase — DocumentVersion throws on updating, and the repository history records "immutable versions, posted-record locking, mandatory change reason." There is no valid merge of "posted" and "posted differently." Accounting resolves conflicts the opposite way: by appending a compensating entry that preserves both facts. Repo Inference

Contrast "upload document". A document is content-addressed by SHA-256, additive, and order-independent. Two devices uploading two documents yields two documents; no invariant is touched, and add-only merge is semantically correct. The same holds for "update draft note" — a draft carries no external commitment, so last-write-wins is acceptable — and for "cache reference data", which is read-only replication with no writes to merge. This is the precise dividing line. Inference

Challenging the assumption where it deserves challenge. There is a legitimate offline pattern for accounting, and it is not synchronisation. Queue intents (commands), never states: the device records "I intend to create a bill with these fields" plus a client-generated idempotency key; on reconnect the server replays the intent, validates it against current state, assigns the sequence number at commit time, and may reject it. Authority never leaves MySQL. The UI must then show "pending submission" as a visibly distinct state from "recorded" — conflating them is how users come to believe an unposted entry is posted. This is deferred submission, not offline sync, and it needs no P2P whatsoever. Inference

Fully decentralised ERP (reading F)

Preserving the four invariants across multiple authoritative replicas requires distributed consensus — Raft or Paxos — which needs a live quorum. That defeats the entire purpose for disconnected devices, and buys enormous operational complexity for no business benefit in a single-tenant ERP. The systems that do run multi-master ledgers purchase it with consensus latency and append-only immutability, and even they do not model approval chains or HR hierarchies. Not recommended, on architectural grounds rather than difficulty. Inference

Section 11

Five architecture options

Option A — WebRTC only

Laravel authenticates and signals; browser-to-browser DataChannel carries payload; coturn provides STUN and TURN fallback. Zero install, works on both platforms. Costs: greenfield JavaScript in a repo with no runtime JS dependencies, new UDP/TLS infrastructure, and a 60–70% relay rate in the corporate networks that are the actual target.

Option B — LAN P2P with a native agent

Signed desktop agents for Windows and macOS perform mDNS discovery and direct socket transfer. Best raw performance and the only option delivering true device discovery. Costs: two native applications that do not exist today, code signing, MDM distribution, auto-update, and vulnerability to the multicast suppression and client isolation common on corporate WLANs.

Option C — Tailscale / Headscale

Enrol devices into an overlay network; every device becomes routable; the existing HTTP stack works unchanged across networks. Lowest effort by a wide margin and strongest security story. Costs: privileged client software on every machine (disqualifying for some IT policies) and either per-seat fees or self-hosting Headscale.

Option D — libp2p with a coordination service

A Go or Rust daemon alongside Laravel, with js-libp2p or native peers. Most capable, least justified: a new language runtime and deployment unit for a two-node problem, with no PHP participation possible.

Option E — Hybrid (recommended)

MySQL remains the sole authority. Each need is routed to the simplest adequate transport, and every transfer is explicitly labelled by the path it actually took.

The scores that decide it

  • WebRTC · Internet P2P · Acceptable — it connects, but the verified 60–70% enterprise relay rate means the majority of sessions are not peer-to-peer.
  • WebRTC · Deployment ease · Poor — coturn needs UDP 3478, a wide UDP relay port range, and ideally TCP/TLS 443, against a compose file that publishes one HTTP port today. TURN on 443 also collides with Nginx unless separately addressed.
  • libp2p · Laravel integration · Poor — no PHP implementation means Laravel cannot be a peer, only a credential issuer, so the new daemon buys nothing the WebRTC option does not.
  • Tailscale · Browser support · Not suitable — it operates at the network layer, so it cannot serve a zero-install browser feature. This is also why it needs no application code.
  • Tailscale · Infrastructure cost · Poor — $6–18/user/month is significant per-seat cost for an ERP, though Headscale removes it.
  • LAN P2P · Fallback · Poor — when discovery fails, which it does on isolated corporate WLANs, there is no graceful degradation without building the server path anyway.
  • Hybrid · Offline · Good — earned not by P2P but by the command-outbox pattern of §10, which is the only offline approach safe for accounting.

(2) Install Reverb and build server-side realtime, which is the correct substrate for presence, device pickers and signalling. Section 14

Proof of concept — standalone, outside the ERP

The POC should be a small separate Laravel application plus a single-page client. It must not touch Aureus. Its purpose is not to demonstrate that WebRTC works — that is established — but to measure the direct-connection rate on the customer's real networks, which is the only number that decides go or no-go.

TEST 1
Windows Chrome ↔ macOS Safari

Establish a DataChannel between the two target platforms and exchange a known payload.

Pass: byte-identical payload, both directions, Safari included — it is the most divergent implementation.
TEST 2
Same LAN

Both peers on one office subnet. Record which candidate type wins.

Pass: selected pair is host/host, confirming LAN-direct despite mDNS obfuscation.
TEST 3
Different networks

One peer on office WAN, one on home broadband, one on mobile tethering.

Pass: connection succeeds; record srflx versus relay for each pairing.
TEST 4
NAT traversal census

The decisive test. Run 1–3 across every real network the customer uses, including the guest and corporate WLANs.

Pass: ≥70% of pairings achieve a non-relay path. Below that, abandon P2P — you are building a relay service.
TEST 5
Failure → fallback

Block UDP at the firewall, then block TURN, and confirm each degradation step.

Pass: falls direct → relay → plain server transfer with no user-visible failure, only slower.
TEST 6
Authentication

Attempt a transfer with no grant, an expired grant, another user's grant, and a grant for a different company.

Pass: all four refused at the receiving peer, not merely hidden in the UI.
TEST 7
Peer revocation

Revoke the sending device mid-transfer.

Pass: in-flight transfer aborts at the next heartbeat; no new grant issues; revocation is audited.
TEST 8
Encrypted transfer + tamper

Confirm DTLS is active, then have a malicious sender flip one byte.

Pass: receiver's SHA-256 check rejects and quarantines; rejection is audited.
TEST 9
Large file

Transfer 100 MB, 500 MB and 2 GB with chunking and bufferedAmount backpressure.

Pass: completes without unbounded memory growth on either peer; record throughput versus plain HTTPS upload.
TEST 10
Interrupted resume

Sever the network at 40% and reconnect.

Pass: resumes from the recorded offset rather than restarting; final hash matches.

Instrumentation is the actual deliverable. Every run must record the selected candidate pair type, negotiation duration, throughput, relay bytes consumed, and failure cause — written to a table and reported as distributions, not anecdotes. Test 4's percentage and Test 9's throughput-versus-HTTPS comparison are what a reviewer should decide on. A POC that proves connectivity without quantifying the relay rate has proven nothing actionable. Inference

Section 15

Integration into Aureus, if approved

Designed to extend existing subsystems rather than parallel them. No accounting or HR logic is touched; no authority moves out of MySQL.

New tables — three, all additive

  • user_devices — id, user_id, company_id, public_key, label, platform, last_seen_at, revoked_at.
  • p2p_transfer_grants — grant_id, nonce, sender/recipient user+device, company_id, document_id, expected_sha256, max_bytes, expected_fingerprint, expires_at, consumed_at.
  • p2p_transfer_attempts — grant_id, path taken (direct/relay/server), bytes, duration, outcome, failure reason, both peers' signed attestations.

Reuse rather than rebuild

  • Audit: add cases to the existing DocumentAuditAction enum — p2p_grant_issued, p2p_transfer_completed, p2p_transfer_failed, p2p_integrity_rejected — writing to accounting_document_audits. No new audit system. Repo
  • Integrity: reuse checksum_sha256 and the readVerifiedBytes() pattern; the recipient performs exactly the check the server already performs.
  • Validation: reuse ALLOWED_MIME_TYPES and MAX_FILE_SIZE_BYTES (raised as part of prerequisite 1).
  • Permissions: grant issuance calls the existing AccountingPermissions::DownloadDocuments check and assertCompanyAccess(). No new permission model — at most one new accounting_transfer_documents_p2p permission so the capability can be withheld per role.
  • Storage: unchanged. DocumentStorageProvider remains the only writer of canonical bytes.
  • Queue: reuse the database queue for attestation reconciliation and grant expiry sweeps.

New surfaces

  • Routes: POST admin/api/v1/p2p/grants, POST .../signal, POST .../attest, DELETE admin/api/v1/devices/{id} — all auth:sanctum, all company-scoped from the token rather than from request input.
  • Services: DeviceRegistrationService, TransferGrantService, SignalingService — thin, and none of them a data-access path.
  • UI: one action on the existing DocumentAttachmentsRelationManager — "Send to device" — plus a device list on the profile page. The transfer indicator must state the path in plain words: "sent directly", "sent via relay", "sent via server".
  • Monitoring: direct-versus-relay ratio, relay bytes per month, grant issuance rate, integrity-rejection count. The first two are cost and architecture-validity signals; the last is a security signal.
  • Failure handling: every path falls back to plain server transfer, and the fallback is the tested default rather than an error branch.

Final go / no-go

No-go on P2P now. Go on prerequisites, and on phase 2 regardless. The device registry, grant model and audit extensions are worth building on their own merits — they deliver the requested user experience, close real security gaps, and are a precondition for any future peer transport. The peer transport itself should wait behind a measured POC, and should be abandoned outright if the direct-connection rate on the customer's actual networks falls below 70%. If the underlying requirement turns out to be cross-network reachability rather than in-browser transfer, adopt Tailscale or Headscale and write no application code at all. Inference

Assumptions that would change this

  • Assumption Users are primarily on managed corporate networks. If they are mostly on home or mobile networks, relay rates drop toward 20% and WebRTC becomes materially more attractive.
  • Assumption Typical transfers are tens to hundreds of megabytes. At multi-gigabyte media scale the bandwidth argument strengthens considerably.
  • Assumption Installing privileged client software is unacceptable for some users. If every device is MDM-managed, Tailscale becomes the clear winner.
  • Assumption No regulatory obligation requires the server to observe every document transfer. If one does, P2P for documents is disqualified outright.
